# SceneForge .161 — browser transport, existing nodes

User instruction: retain SceneForge frame/storyboard nodes, source/reference resolution, prompt ownership and approval/version flow. Adapt only Gemini connectivity from the user's working test-gemoni-chat extension 0.2.2 (https://github.com/thutrang0807hp-ux/test-gemoni-chat). No Studio UI or extra refinement workflow is imported. The new explicitly paired browser account is selected by the existing account pool. Existing SDK accounts/receipts remain available; no automatic migration or resend of their unknown jobs.

Protocol 5 pairs the SceneForge extension to an existing Gemini tab. Broker Origin/capability checks use the existing fixed extension ID and one-time loopback pairing. Gemini browser pairing never calls cookie export, SDK login or SDK generation. Only the authenticated browser DOM must expose a chat editor. Flow-only pairing still negotiates protocol4. The full on-app ZIP endpoint and standalone ZIP now contain the same 1.7.0 files. Newly required googleusercontent host permission handles browser image reads; unlimitedStorage holds only bounded in-flight replies until delivery, then successful image bytes are removed from extension storage.

Generation uses the same gemini-chat submit/ledger/account selection and result-file endpoints. The backend forwards the exact node prompt and ordered source/product/person references. Extension opens one account-path-pinned tab per turn, waits for visible attachment previews before send, sends once, and reads image or text from its own response. Image reads use browser fetch/canvas first and an authenticated extension fetch fallback to the original Google image URL. Actual bytes are verified with the existing Pillow format/dimension checks and saved through the existing job path to the original scene. The selected browser model is recorded as browser-session rather than falsely claiming an SDK model setting was applied. Browser work is serialized per account and extension.

One durable request ID is dispatched at most once. Queued timeout before dispatch cancels the queue entry; dispatched uncertainty never replays generation. The extension retains a failed turn's tab and marks its model response with the job ID. Explicit Receive targets that original tab/response, even after another response appears; no fallback to the newest image. Worker restart refuses to repeat a possibly sent turn and retries delivery of cached bytes only. Broker accepts idempotent identical late responses and preserves pending results across server restart. After normal scene file/ledger commit, duplicate broker image bytes are removed; only compact job metadata/hash remains. Recovery reports downloading while active, and browser polling has a 5-minute local wait limit rather than incorrectly stopping at 2 minutes.

Existing frame UI remains, including review/versions. The previously hidden quota-confirmed abandon/retry action is available inside collapsed advanced controls for old SDK download failures. No forced regeneration, approval or old-receipt deletion occurs. Flow/video generation and photo/storyboard authorship are unchanged.

Validation: actual broker HTTP routes and actual adapter run/import methods with simulated extension transport prove correct prompt+two references, PNG file commit to the original scene, no SDK call, wrong-key/Origin rejection, idempotent late results, restart bookkeeping, existing-file receipt and read-only recovery. Actual bridge pairing verifies account persistence/selection with SDK/cookie import forbidden and Flow protocol4 retained. Actual injected DOM function runs in Chromium fixtures: two attachments, one send, image bytes and text return, missing upload prevents send, later unrelated responses cannot replace the original receive target. Actual popup code negotiates protocol5 with cookie reads forbidden. Actual service-worker code in a Chrome API harness verifies account-path pinning, cached delivery/restart, no replay and receive without new tab/generation; image cache is cleared after acknowledgement. Legacy SDK receive regression and actual frame inspector/account dialog regressions pass. Cumulative updater verifies payload and preserves unchanged .160 files.

Limitations: no live user Google account or native Windows updater execution was available. DOM selectors and attachment acknowledgements must match Gemini's live UI; blocked/unsupported UI fails without silently dropping references. Pairing verifies an editor, not a successful image generation entitlement. The transport does not recover an old SDK-only conversation automatically, enforce a specific SDK model on the website, or promise 4K output.
