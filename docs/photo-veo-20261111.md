# SceneForge .113 — Photo clip board uses Veo lifecycle

Flow photo generation moves from the old flow/jobs route to the same flow/simple/status, jobs, files, diagnostics, review and stop endpoints as reference-video SFVeoNode. Existing backend account/session/admission/ledger/CLI remain the only dispatcher. No additional model/runtime dependencies.

Original shared helper scripts/ui/veo_lifecycle.js is embedded in both documents. Reference node delegates config validation/model IDs, ownership validation and UI yielding to it. Photo adapter scripts/ui/photo_veo.js implements UI/data bindings for photo beats/parts and reuses the helper. Photo bridge locally maps flow/status to truthful SimpleFlow status/capabilities (ordered single start image, no text-only or end-frame capability); bridge methods for other services retain parent implementations. Supported CLI settings advertised only for gflow-cli-direct; submit requires enabled/native pipeline and an available selected account.

A generation requires a used storyboard start frame, approved individual frame or valid continuity tail. Exactly one actual image is encoded, never an overview grid or silently truncated reference array. Paired storyboard binding reports unsupported rather than discarding end image. Manual confirmation also captures source/settings and per-slot prompt signatures; changes after review stop further sends. Input stamps include actual start bytes SHA256, room/part, current photo signature, prompt, settings and previous-clip identity. Intent checkpoint precedes POST. Source, settings, account selection and input stamp rechecked before sending. Unknown/lost replies block replay. Backend active/unresolved gates remain authoritative.

New jobs carry photoVeoVersion=1 inside existing flowJobs. Legacy recovery excludes only those jobs; other Flow/Muse jobs retain prior paths. New recovery verifies request/store/room/beat/part and decodes real video to verify ratio/duration and derive poster/tail. Imports are idempotent by request ID. Stale inputs retain result in staleClips; wrong ownership prevents import. File persistence and room checks precede clip commit. Successful import updates existing draft counts/manifests. Existing clips are preserved on regeneration, and latest result becomes current; explicit old-version selection updates existing chosenParts and mergeView. Versions are not pruned by this adapter.

Manual missing-slot batches require one user confirmation, send one request at a time and wait for import before next send. Errors/unknown halt. Pause prevents further sends but still receives current result. Reload/switch never silently resumes queued generation. Stop is restricted to active requests owned by this room. Automatic existing photo pipeline advances one submitted slot and settles using the new recovery path. Both use existing consent flow; no exports are automatic.

Short codec tail tolerance mirrors Veo: only new Flow clips targeting 8s with tail and <=.15s deficit get readiness tolerance, while actual c.duration/sourceDuration remain unchanged for hold-frame preview/export. Other short clips remain reviewable. Legacy/Muse readiness stays unchanged.

Tests: scripts/analysis/check_photo_veo.py uses Chromium, fake backend receipts and real decoded 7.933333s MP4. Checks persisted intent before each POST, one-image/native endpoint payload, duplicate block, idempotent import, real metadata, draft handoff/source duration, regeneration preserves clips, version selection, lost reply/no resend, wrong room, stale isolation, settings without generation, unsupported pairs, two-slot sequential batch, pause after first request. check_frame_identity.py and check_storyboard_guide.py regressions passed. Both documents' inline JavaScript parsed. Installer payload checksum/source bytes verified; no live Flow generation or Windows updater run.
